# Reviewed Android PDF compatibility repair

This app repairs its PDF-to-file path for exactly `expo-print` 58.0.6. The installed SDK estimated ten pages for a generated document independently parsed as two pages. A separate first request created valid PDF bytes but left its JavaScript promise pending. The source has lifecycle gaps that can leave a request without a terminal callback; these observations do not prove which gap caused that first pending request.

The config plugin patches only `PrintModule.printToFile` plus module task retention, shutdown and the native `ReliablePdfVersion: 1` capability. It adds `ReliablePdfRenderTask.kt`. The system-print HTML and PDF-URI preview paths retain their upstream implementation. The app checks the capability marker before using the repaired Android path, so Expo Go and an older installed binary cannot silently use the SDK's estimated count.

The task retains its WebView until terminal cleanup, waits for layout completion before writing, and handles layout/write failure or cancellation, renderer loss and a 60-second callback deadline. Callback state transitions run on the Android main looper. A terminal guard schedules one cleanup pass after the current native callback unwinds; it attempts document completion, cancellation where needed, descriptor closure and WebView disposal before releasing the module's strong reference. Timeout/cancellation reports that completion was unconfirmed, and does not delete or adopt a potentially written file.

After write completion, the writer descriptor is closed and a worker uses Android `PdfRenderer` to read the actual page count from the generated file. This keeps the main-looper deadline responsive. The worker owns its reader descriptor and closes it before delivering a result; if cancellation/timeout already won, that late result is discarded. A timeout does not claim that an underlying native file inspection stopped instantly. The file must be between 64 bytes and 25 MiB, and contain 1–500 pages. File creation must succeed before opening a truncating descriptor, so an unexpected name collision preserves the existing file. The PDF WebView disables JavaScript, network loads, file access and content-provider access. Export documents and selected images are supplied inline; these settings do not affect other application WebViews or host policy.

The API-26 renderer-loss callback is isolated in a separate client class instantiated only on Android 26 or newer. The ordinary client remains usable at the app's Android 24 minimum. Runtime verification currently targets the owned Android 35 emulator; Android 24/25 and iOS are not claimed as tested by this repair.

## Reproducibility and guards

`app.json` registers `./plugins/withReliableExpoPrint`. The plugin runs during Android prebuild and checks the installed package version, normalized upstream source hashes, the reviewed fragment/helper hashes and the patched module hash before writing. It refuses unrecognized edits or a different package version. Repeated application is a no-op; an absent owned helper can be restored only when the module matches the known original/patched hashes. Temporary writes are renamed into place after validation.

Expo SDK 58 normally selects the package's precompiled Android publication. Therefore `package.json` must explicitly include `expo.autolinking.android.buildFromSource: ["expo-print"]`. The plugin verifies that setting. Without it, editing Kotlin would not affect the packaged native module. Fresh `npm ci` followed by Android prebuild reapplies the repair from version-controlled sources; no extra package or SDK download is needed. The native build must show the `:expo-print` source project and package both the helper class and capability marker. A normal reload cannot add this native repair to an old APK.

`patch-manifest.json` records the reviewed SHA256 values. Source-bound tests cover fresh application, idempotency, changed version/source/helper rejection, source-build configuration and native lifecycle structure. They do not emulate Android WebView callbacks. The compiled APK and repeated real PDF generation/page-count comparison remain required runtime gates.

## Provenance

The narrow module replacement is based on the installed [Expo Print Android sources](https://github.com/expo/expo/tree/main/packages/expo-print/android/src/main/java/expo/modules/print), version 58.0.6, under the Expo MIT license copied in [EXPO_LICENSE.txt](EXPO_LICENSE.txt). Original source fixtures are kept only for patch verification, not as a second runtime implementation. The added task is application compatibility code using the same Android print attributes and Expo result types.

Primary API references: [Android HTML printing and WebView retention](https://developer.android.com/training/printing/html-docs), [PrintDocumentAdapter lifecycle](https://developer.android.com/reference/android/print/PrintDocumentAdapter), and [PdfRenderer page count and descriptor ownership](https://developer.android.com/reference/android/graphics/pdf/PdfRenderer). Older Expo issues about null write errors or the system-print busy flag are related history, not a demonstrated root cause for this request.
